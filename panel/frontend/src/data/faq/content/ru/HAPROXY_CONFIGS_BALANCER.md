# Алгоритмы балансировки

Алгоритм решает, на какой сервер пула уйдёт следующее соединение.

| Алгоритм | Когда брать |
|---|---|
| roundrobin | По кругу. Для коротких однотипных запросов: API, статика |
| leastconn | На сервер с наименьшим числом активных соединений. Для долгих: WebSocket, gRPC, базы |
| source | Сервер выбирается по хешу IP клиента — дешёвая привязка без cookie |
| first | Всё на первый живой сервер; остальные простаивают. Это схема «основной плюс резерв», а не балансировка |
| static-rr | Как roundrobin, но без динамического учёта весов; чуть быстрее и проще |

## Веса и резерв

- Вес задаёт долю трафика: сервер с весом 2 получит вдвое больше, чем с весом 1. Так выравнивают ноды разной мощности.
- Резервный сервер (backup) принимает трафик только когда все основные недоступны.

## Полезно знать

- На очень быстрых ответах (единицы миллисекунд) счётчик соединений не успевает обновляться — roundrobin даст более ровное распределение, чем leastconn.
- Привязка по IP держится, пока состав пула не меняется: добавили или убрали сервер — часть клиентов переедет. Нужна настоящая липкость — используйте привязку через cookie.
- Смена алгоритма применяется перезагрузкой конфига и не рвёт текущие соединения.
- Нагрузка легла неравномерно — сначала проверьте проверки живости: вероятно, часть пула помечена недоступной.
