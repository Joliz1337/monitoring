# Проверки живости

Балансировщик регулярно проверяет серверы пула и выводит из ротации те, что не отвечают.

## Виды проверок

| Вид | Что делает | Когда использовать |
|---|---|---|
| TCP | Открывает соединение на порт и закрывает | Любой протокол: базы, VPN-инбаунды, произвольный TCP |
| HTTP | Запрашивает указанный путь и смотрит код ответа | Веб-приложения, где важен не порт, а работоспособность |
| TLS + сайт-маскировка | Делает рукопожатие с SNI сервера и запрашивает страницу | Инбаунды за REALITY, где TCP-проверка обманывает |

## Проверка по сайту-маскировке

TCP-проверка доказывает ровно одно: порт принял соединение. Задушенный по пути или упавший инбаунд за живым портом она не отличит — сервер останется в ротации, а трафик через него ходить не будет.

У REALITY есть запасной ход: клиенту, который не подошёл, сервер отдаёт настоящий сайт-маскировку. Значит живой сервер обязан ответить на обычное TLS-рукопожатие со своим SNI. Эта проверка так и делает — рукопожатие, `GET /`, и ответ должен быть внятным HTTP: 2xx, редирект или даже 403/404 годятся, потому что все они доказывают, что за портом работает сервер. Молчание или 5xx — сервер уходит из ротации.

Проверяется вся цепочка: порт открыт, ядро приняло соединение и сумело сходить на сайт-маскировку.

- **SNI** — обязательно домен из `serverNames` инбаунда. С чужим именем сервер оборвёт связь, и проверка будет падать всегда.
- **Интервал.** Каждая проверка — полное TLS-рукопожатие плюс реальный запрос ядра наружу. У одиночного правила интервал 30 секунд, у пула задаётся у каждого сервера; при значении 5 секунд с одной ноды набегают десятки тысяч запросов в сутки на сайт-маскировку.
- **Только TCP-правила.** Для HTTPS-правил панель терминирует TLS сама, там работает обычная HTTP-проверка.

## Параметры

- **Интервал** — как часто проверять. Чаще — быстрее реакция, но больше лишнего трафика.
- **Падений до отключения** — сколько неудач подряд, чтобы вывести сервер из ротации.
- **Успехов до возврата** — сколько удачных проверок, чтобы вернуть его обратно; защищает от «мигания».
- **Медленный старт** — вернувшийся сервер получает нагрузку не сразу, а нарастающе.

## Полезно знать

- Сервер жив, но помечен недоступным — проверьте, что проверка идёт на тот порт, что файрвол её пропускает, а страница проверки отвечает кодом 200.
- Если на бэкенд включена передача PROXY protocol, проверки тоже должны идти с ним, иначе бэкенд рвёт соединение и сервер будет вечно недоступен. Панель включает это автоматически.
- Слишком частые проверки на большом пуле создают заметный фон запросов — для десятков серверов хватает интервала в несколько секунд.
- Проверка по HTTP должна бить в лёгкий путь без обращений к базе, иначе она сама станет источником нагрузки.
